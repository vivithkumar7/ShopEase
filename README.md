# ShopEase Product Service

An independent FastAPI product-management service backed by Azure SQL
Database. Products persist across application and container restarts.

## Technology stack

- **Backend:** Python 3.11+, FastAPI, Uvicorn, and Pydantic
- **Persistence:** Azure SQL Database with the Microsoft `mssql-python` driver
- **Containerization:** Docker, Dockerfile, and Docker Compose
- **API testing:** Swagger UI and Postman
- **Version control:** Git and GitHub

See [PROJECT_GUIDE.md](PROJECT_GUIDE.md) for a detailed source walkthrough,
project structure, setup, Docker testing, Postman test cases, and GitHub
publishing steps.

## FastAPI request flow

FastAPI is a Python framework for building HTTP APIs. It uses Python type
annotations and Pydantic schemas to validate and convert request data and to
generate an OpenAPI specification. An ASGI server such as Uvicorn receives
network traffic and passes each request to the FastAPI application. FastAPI
matches the HTTP method and URL to a route, validates path parameters, query
parameters, and JSON bodies, and then calls the route function. The route
delegates product operations to the service layer. FastAPI serializes the
response as JSON and returns it with the declared HTTP status code.

`app/main.py` initializes the application and registers the product router.
`app/routers/product_routes.py` defines endpoints using `APIRouter`.
`app/schemas/product_schema.py` defines validated request and response shapes.
`app/models/product_model.py` defines the product data structure, while
`app/services/product_service.py` delegates catalog operations to the SQL
repository.
`app/config/settings.py` loads application configuration from `.env` and
environment variables. Database tables and migration metadata live in the
`shopease` SQL schema.

FastAPI generates API documentation from the registered routes and schemas:

- Swagger UI: <http://127.0.0.1:8000/docs>
- ReDoc: <http://127.0.0.1:8000/redoc>
- OpenAPI JSON: <http://127.0.0.1:8000/openapi.json>

## API reference

All product endpoints use the `/api/products/` path prefix.

| Method | Path | Purpose | Success status |
| --- | --- | --- | --- |
| `POST` | `/api/products/` | Create from a JSON request body | `201 Created` |
| `GET` | `/api/products/` | List products with optional category and pagination | `200 OK` |
| `GET` | `/api/products/{product_id}` | Get a product by path parameter | `200 OK` |
| `PUT` | `/api/products/{product_id}` | Replace product details, preserving its creation date | `200 OK` |
| `DELETE` | `/api/products/{product_id}` | Delete a product | `204 No Content` |

List products with query parameters, for example:
`GET /api/products/?category=Electronics&skip=0&limit=10`. Category matching
is case-insensitive. An empty catalog or a filter with no matches returns an
empty JSON list. Products persist after the process restarts.

## Test the API

Start the application locally with Uvicorn or in Docker using the instructions
below, then use Swagger UI at <http://127.0.0.1:8000/docs> or
<http://localhost:8003/docs> to try the endpoints interactively.

To test with Postman, create requests against the corresponding base URL:

- Local: `http://127.0.0.1:8000/api/products/`
- Docker: `http://localhost:8003/api/products/`

For `POST` and `PUT`, select **Body > raw > JSON** and use the example request
below. Create a product first to obtain an ID, then use that ID in the `GET`,
`PUT`, or `DELETE` path. Products remain in the database until deleted.

Example create or update request:

```json
{
  "name": "Headphones",
  "description": "Wireless headphones",
  "price": 2500,
  "stock_quantity": 20,
  "category": "Accessories",
  "status": "Active"
}
```

The description is optional and limited to 1000 characters. Names and
categories must contain non-whitespace text and are limited to 100 characters.
Price must be positive, below `1000000000000000`, and have at most four
decimal places to match the database `DECIMAL(19,4)` column. Stock quantity
must be a non-negative integer, and status must be `Active` or `Inactive`.
Product IDs are generated by the
service; clients cannot supply or update them. Invalid input and malformed or
non-positive IDs return `422 Unprocessable Entity`. Unknown IDs return
`404 Not Found`; unexpected server errors are logged and return a generic
`500 Internal Server Error`.

## Set up the Python environment

Run these commands from the `shopease-product-service` directory in
PowerShell. Use Python 3.11 or newer:

```powershell
py --version
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip check
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# Edit .env with your Azure SQL host, database and authentication settings.
python -m app.db.migrate --database ShopEase
uvicorn app.main:app --reload
```

A virtual environment isolates this service's packages from other projects
and system Python. `requirements.txt` lists the dependencies needed to
recreate the environment. The local development server runs at
<http://127.0.0.1:8000>.

The configured database name must be the ShopEase application database, not
`master`. Migrations verify the live database name and Azure SQL engine edition
before changing it. The `--database` argument must exactly match `SQL_DATABASE`.
Migrations are not run automatically during application startup.

For SQL authentication, configure `SQL_HOST`, `SQL_DATABASE`,
`SQL_AUTHENTICATION=SqlPassword`, `SQL_USER`, and `SQL_PASSWORD` in the
untracked local `.env` file. For a signed-in Azure CLI/developer identity, set
`SQL_AUTHENTICATION=ActiveDirectoryDefault`; omit the SQL user and password.
Azure connections use encryption and validate the server certificate.

Install the optional test dependencies and run the automated API tests with:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

`requirements-dev.txt` includes the application requirements, pytest, and
HTTPX2 (used by FastAPI's test client); these test-only packages are not added
to the Docker runtime image.

## Docker fundamentals

A Docker image packages the application, its dependencies, and its runtime
instructions. A container is an isolated running instance of that image. Each
Dockerfile instruction contributes a repeatable layer to the image:

- `FROM python:3.12-slim` provides a small Python runtime image.
- `WORKDIR /service` sets the directory used by subsequent build and runtime
  commands.
- `COPY requirements.txt .` copies the dependency list first so Docker can
  reuse the installed-dependency layer when only application code changes.
- `RUN pip install --no-cache-dir -r requirements.txt` installs the
  application dependencies into the image without retaining pip's download
  cache.
- `COPY app ./app` adds the FastAPI source code to the image.
- `EXPOSE 8003` documents the port the application listens on; port publishing
  is configured separately when starting the container.
- `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8003"]`
  starts Uvicorn on all container interfaces so the published host port can
  reach the application.

The `compose.yaml` file builds the service, publishes port 8003, and passes
the database connection settings from environment variables or `.env`. Copy
and edit `.env.example` before using Compose. Apply migrations before starting
the application:

```console
docker compose build
docker compose run --rm product-service python -m app.db.migrate --database ShopEase
docker compose up --build -d
docker compose ps
docker compose logs
docker compose down
```

`docker compose down -v` also removes named volumes; this service does not
currently define any volumes. Use Compose to manage this container rather
than mixing Compose commands with the standalone `docker run` instructions
below.

Alternatively, build and run the service without Compose:

```console
docker build -t shopease-product-service .
docker run --rm --env-file .env shopease-product-service python -m app.db.migrate --database ShopEase
docker run -d --name shopease-product-container --env-file .env -p 8003:8003 shopease-product-service
docker ps
docker logs shopease-product-container
```

In `-p 8003:8003`, the first port is on the host and the second is in the
container. The container listens on port `8003`; open
<http://localhost:8003/docs> to use Swagger UI. `.dockerignore` keeps virtual
environments, Python and test caches, Git metadata, temporary files, and
`.env`-style local configuration, secret files, and private keys out of the
build context. This reduces unnecessary files sent to the Docker engine and
helps prevent local credentials from being included in an image. Migrations
must complete successfully before the API container is started. Stop, restart,
and remove the container with
`docker stop shopease-product-container`,
`docker start shopease-product-container`, and
`docker rm -f shopease-product-container`.

Run the included standard-library smoke test against the running Docker
container:

```powershell
.\.venv\Scripts\python.exe scripts\smoke_test.py --base-url http://localhost:8003
```

The script checks CRUD operations, validation failures, category filtering,
pagination, and not-found responses. It uses only the Python standard
library. See [PROJECT_GUIDE.md](PROJECT_GUIDE.md) for full Postman steps,
GitHub publishing instructions, and screenshot evidence checklist.

## Database migrations

The ordered migrations create `[shopease].[products]`, the
`[shopease].[__schema_migrations]` history table, and the
`[shopease].[__migration_lock]` coordination table. The runner:

- requires an explicit `--database` matching `SQL_DATABASE`, rejects `master`,
  and verifies the live database name and Azure SQL engine edition;
- serializes concurrent runners with a transaction-owned application lock
  named for the `shopease` schema and a row lock in that schema;
- applies migrations and history updates in the same transaction;
- records a SHA-256 checksum and refuses edited, missing, or unknown migration
  versions; and
- checks each migration's postcondition before recording it and verifies the
  latest migration's final schema before reporting success.

If a migration fails or postconditions do not match, the transaction is
rolled back and the command exits with an error. Re-running the same migration
is a no-op only after its checksum and live schema are verified. Add a new
numbered forward migration; never edit a migration already applied to a
database.
