SHOP EASE · PROJECT REPORT01 / OVERVIEW
01 · Project overview

Purpose and scope

ShopEase Product Service exposes a small, independent HTTP API for managing catalog products.

Clients send JSON requests to FastAPI routes. Pydantic validates request data, the route delegates to the product service, and a repository performs data access. The production repository is designed for Azure SQL Database; an in-memory repository is retained for isolated API tests.

Core capabilities
  • Create a product
  • List, category-filter, and paginate
  • Read one product by ID
  • Replace product fields
  • Delete a product
Operational goals
  • Typed request and response schemas
  • Stable REST status codes
  • Containerized Uvicorn service
  • Explicit and guarded SQL migrations
  • Testable repository/service boundary

SHOP EASE · PROJECT REPORT03 / ARCHITECTURE
03 · Architecture and request flow

Layered request path

Each request passes through a short sequence of typed layers. This lets validation happen before business logic or a database operation is attempted.

Client
Swagger UI · Postman · web client
↓ HTTP / JSON
Uvicorn
ASGI server listening on port 8003 in Docker
↓ ASGI request
FastAPI router + Pydantic schema
Route matching, field validation, HTTP status
↓ validated values
Product service
Catalog operations
↓ repository calls
SQL repository → [shopease].[products]
Azure SQL Database

Response path

The repository returns a product model, the response schema shapes it, and FastAPI serializes JSON with the route's declared status code. Unexpected exceptions are logged server-side and return a generic 500 response.

Design benefits

  • Input validation is consistent and visible in generated OpenAPI docs.
  • The service layer provides a stable seam between routes and storage.
  • Tests can inject an in-memory service without requiring SQL.
  • The SQL repository uses parameterized statements rather than string-built values.

List and error behavior

Guarding the API boundary

Pydantic schemas reject malformed or out-of-range input before it reaches the product service. Unexpected fields are forbidden so client mistakes are not silently ignored.

InputRuleExample rejected
name / categoryTrimmed, non-empty, max 100 charsSpaces only
descriptionOptional, max 1000 charsWhitespace-only text
priceStrict positive number, max 4 decimals0, negative, 0.00001
stock_quantityStrict integer ≥ 0-1 or a decimal
statusActive or InactivePending
product_idInteger greater than zero0 or non-numeric text

HTTP status summary

Read or update succeeded.
201 Created
Product created.

422 Unprocessable Entity
Invalid request, path, or query.
500 Internal Server Error

SHOP EASE · PROJECT REPORT06 / DATABASE
06 · Database and migrations

Persistence and schema safety

Product records are designed for Azure SQL Database. Application tables and migration state are isolated in the shopease schema.

ObjectPurpose
[shopease].[products]Product data, PK, checks, and category index
[shopease].[__schema_migrations]Applied migration versions and SHA-256 checksums
[shopease].[__migration_lock]Application-level migration lock record

Migration safeguards

  1. Explicit CLI requires --database to match SQL_DATABASE and refuses master.
  2. Engine and current database are checked before DDL.
  3. Migrations run in order under a database application lock and a transaction.
  4. Previously applied files are checksum-verified; edited, missing, or unknown versions fail.
  5. Postconditions are checked before recording the migration and again for the latest schema.
  6. Failures roll back and propagate; app startup does not apply schema changes.
Not live-applied: no SQL_HOST was present in the local environment when evidence was captured. A real Azure SQL migration and database CRUD still need to be run against the intended database.

Money precision

API price rules align to DECIMAL(19,4) so values outside the database range or scale are rejected rather than silently rounded.
